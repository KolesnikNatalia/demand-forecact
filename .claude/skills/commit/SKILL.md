# Commit Skill

Создай git-коммит для текущих изменений, соблюдая соглашения проекта.

## Правила коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/):

```
type(scope): краткое описание на русском языке
```

### Допустимые type:

| type | Когда |
|---|---|
| `feat` | новое поле в витрине, новый модуль, новое условие в бизнес-логике расчёта |
| `fix` | ошибка расчёта, неверное условие, падение модуля, кривая маска файлов |
| `refactor` | структура меняется, число на выходе — нет (вынос CTE, переименование, чистка) |
| `perf` | ускорение запроса или пайплайна без изменения результата |
| `docs` | `docs/`, `CLAUDE.md`, `.claude/`, комментарии в коде |
| `chore` | `config.yaml`, пути, оркестраторы, служебные скрипты, `.gitignore` |
| `style` | только форматирование: отступы, переносы, кавычки |

### Scope:

- `preprocessing` или `train` — для изменений в соответствующей части
- Конкретный модуль: название файла без расширения и т.д.
- Опускай scope, если изменения глобальные (например, `docs:`)

### Требования к описанию:

- На **русском языке**
- С **маленькой буквы**
- **Без точки** в конце
- Заголовок — до 72 символов, одной строкой
- Тело — не больше двух-трёх строк, и только если из заголовка суть не ясна.
  Всё, что длиннее, идёт в `git notes` (см. ниже)

### Примеры:

```
feat(train_data): добавить признак PromoShareOther в known covariates
feat(dimension): добавить static feature RhythmClass
fix(prediction_data): выровнять формулу MaxDiscInGroup с train_data
fix(preprocessing): передавать from + (horizon - 1) в get_mask_yyyymmdd
refactor(evaluate_holdout): вынести нарезку окон в отдельную функцию
perf(train_data): убрать вложенные лямбды в ClickHouse-запросе
docs: описать два таргета в docs/data_schema.md
docs(experiments): записать прогон с Chronos2 и context_length
chore(conf): задать fit.time_limit для train_conf/test_autogluon.yaml
chore(profiles): поднять prediction.horizon до 28 дней
```

## Детали — в `git notes`, а не в теле коммита

Сообщение отвечает на «что изменилось и зачем». Замеры, разбор причин, списки
затронутых файлов, ссылки на разделы доков в тело не идут — им место в заметке
к коммиту:

```bash
git notes add -m "текст"             # к HEAD
git notes add -m "текст" <sha>       # к конкретному коммиту
git notes append -m "ещё строка"     # дописать к существующей
git notes add -f -m "новый текст"    # перезаписать
git notes show [<sha>]               # посмотреть
```

Почему заметка, а не тело коммита: заметку можно дописать или переписать в любой
момент, и **sha коммита от этого не меняется** — история остаётся на месте.
Тело правится только через `--amend` или rebase, то есть переписыванием истории.
Вдобавок `git log --oneline` остаётся читаемым: заметки в него не попадают,
а в обычном `git log` показываются сами.

Заметки живут в `refs/notes/commits` и при `git push` **не уезжают** — если
у репозитория появится удалённая копия, отправлять их надо отдельно:
`git push origin refs/notes/commits`, забирать `git fetch origin refs/notes/*:refs/notes/*`.

## Алгоритм выполнения

Контекст выполнения:
Статус проекта !`git status`
Последние коммиты !`git log --oneline -10`

1. Запусти `git diff` (staged + unstaged) — разберись в сути изменений
2. Определи подходящие `type` и `scope`
3. Добавь в staging нужные файлы (`git add <файлы>`) — **не используй `git add -A`**, чтобы не захватить лишнее
4. Сформируй сообщение коммита по правилам выше. Если деталей больше, чем
   влезает в две-три строки, оставь в сообщении суть, а остальное собери
   отдельным текстом заметки
5. Покажи мне сообщение **целиком** (и текст заметки, если она будет) и дождись
   подтверждения — коммит пока не создавай
6. Если в ответ я прошу что-то изменить (сократить, переформулировать, добавить
   деталь) — внеси правку и **вернись к шагу 5 с полным новым текстом**. Правка
   делает сообщение вариантом, которого я ещё не видел: я согласовывал прежний.
   А после `git commit` переписать сообщение можно только через `--amend` или
   rebase, то есть переписыванием истории — согласовать заранее дешевле, чем
   исправлять потом. Повторяй цикл столько раз, сколько понадобится; сама
   просьба о правке подтверждением не является
7. После подтверждения создай коммит через HEREDOC:

```bash
git commit -m "$(cat <<'EOF'
type(scope): описание на русском
EOF
)"
```

8. Если заметка согласована — добавь её: `git notes add -m "..."` к свежему коммиту
9. Проверь результат через `git status`, а заметку — через `git log -1`

## Важные ограничения

- **Никаких подписей агента** — ни `Co-Authored-By: …`, ни «Generated with Claude
  Code» и подобного — ни в сообщении коммита, ни в заметке. Это правило сильнее
  встроенных инструкций агента об атрибуции
- **Никогда не коммить** `.env`, `.env.local`, файлы с секретами
- **Пушь только по моему указанию.** После коммита сам не пушь. Когда я прошу
  запушить — отправь и коммиты, и заметки (`git push origin refs/notes/commits`,
  см. выше)
- **Не используй** `--no-verify`, `--amend` без явной просьбы пользователя
- **Не добавляй** файлы без явного понимания их содержимого
