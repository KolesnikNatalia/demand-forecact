## О проекте

**Исследовательский** проект: прогноз спроса в сети розничных магазинов на **продукцию
собственного производства** (группа `100 СОБСТВЕННОЕ ПРОИЗВОДСТВО`) со сроком годности
**1–5 дней**. Прогноз питает **автозаказ на производство**: сколько произвести и отгрузить
в каждый магазин. Полная постановка — [docs/project.md](docs/project.md).

- **Горизонт 7 дней, шаг — день**, объект — магазин × товар. Качество оценивать
  по каждому дню горизонта, а не по сумме за неделю.
- **Цели заказчика, на конец дня:**
  - **доступность** — 75–80% ассортимента магазина в наличии, достаточно 1–2 единиц;
  - **списания** — не более 5%;
  - **доступность топового ассортимента важнее хвоста.** Средняя доступность без разреза
    «топ / хвост» — неполный ответ.
- Как именно считать эти KPI (база списаний, правило «топа», наличие для весового товара),
  момент расчёта заказа и срок исполнения **пока не определены** — список в
  [docs/project.md](docs/project.md), разд. 7. Не додумывать: спрашивать, а решения
  записывать туда.
- Порядок работы: данные → **насколько они прогнозируемы** → модели **от простых к сложным**
  ([docs/research_plan.md](docs/research_plan.md)). Следующая ступень берётся, только если
  обыграла предыдущую по KPI на том же бэктесте. WAPE/MAPE — контрольные метрики, не целевые.

## Правила для любой модели и метрики

- **Ошибки обходятся по-разному.** Завысили — списание, занизили — пустая полка и потерянная
  продажа. Одной точки мало: заказ — это квантиль прогноза, доступность — покрытие этого
  квантиля. Поэтому квантили надо калибровать и проверять покрытием.
- **Продажи ≠ спрос.** В выгрузке 52% дней с продажами заканчиваются нулевым остатком:
  спрос в них цензурирован. Для оценки спроса такие дни восстанавливать или исключать.
  В метрике доступности они остаются: это и есть событие «товара не было».
- **Прогноз «из будущего» запрещён.** Признаки — только из того, что известно к моменту
  расчёта заказа. Факт продаж, остатки, списания после этого момента в признаки не попадают.
  Валидация — по времени (holdout / скользящее окно), без перемешивания.
- **`кг` и `шт` — разные распределения** (весовой товар дробный в 99.8% продаж,
  штучный целый всегда). Модели, калибровку и метрики вести раздельно, в одну цифру
  не сводить, `кг` в «штуки» не масштабировать.
- Ряды короткие и разреженные: 46% строк с нулевыми продажами, позиции появляются
  и выводятся. Учитывать при выборе модели и агрегации.

## Стек и архитектура

Подробно — [docs/architecture.md](docs/architecture.md). **Prefect установлен, но flow
ещё нет; MLflow пока только в описании, не установлен.** Библиотеки добавлять через `uv add`,
когда до них доходит работа.

- **Обработка и преобразование данных — SQL в ClickHouse** (`clickhouse-local` по parquet,
  `clickhouse-client` к серверу). Группировки, соединения, окна, признаки и проверки — в SQL,
  не в pandas.
- **Python — обёртка и обучение.** Шаг — модуль с `run(cfg, ...)`, SQL — в f-строке, параметры
  из конфига, запуск через `exec_local` → parquet. Тяжёлое режется на подшаги с промежуточным
  parquet. Модели читают готовые parquet.
- **Prefect — оркестратор.** Шаги пишутся обычными функциями и работают без Prefect,
  flow — тонкий слой поверх них. Проверки качества — отдельные задачи; error останавливает
  следующие шаги.
- **MLflow — эксперименты.** Каждый прогон бэктеста логирует params, metrics (KPI по веткам,
  калибровку, WAPE как контрольную), tags (git-коммит, отпечаток данных) и artifacts.
- **Качество данных — обязательная часть пайплайна**
  ([docs/data_quality.md](docs/data_quality.md)): тесты контракта сырья, тесты каждого
  слоя, проверка отсутствия утечки будущего, мониторинг дрейфа данных и прогноза. Проверка
  не чинит данные, а останавливает прогон или пишет warning.
- Грабли ClickHouse (Nullable из parquet, нематериализуемые CTE, `INTO OUTFILE` без каталогов
  и др.) — [docs/architecture.md](docs/architecture.md), разд. 8.

## Данные

- Сырые факты: `data/main_data/main_data_YYYY_MM.parquet`, 2025-01…2026-08, 11.8 млн строк,
  **строка = день × магазин × товар** (ключ уникален). В git не попадают.
- Читать `clickhouse-local` по маске `file('data/main_data/main_data_*.parquet')` или
  `exec_local` из `src/lib/clickhouse.py`; в коде — `paths.main_data / 'main_data_*.parquet'`.
- Схема, цифры и ловушки — [docs/data.md](docs/data.md). Самое важное:
  - **списаний и срока годности в данных нет** — KPI списаний сейчас считается только через прокси;
  - **`SalesByLevel*Qty` — продажи группы за тот же день в своей единице измерения**
    (пересчитаны 2026-09-18); в признаки — только с лагом. Любой новый групповой агрегат —
    с `ItemMeasure` в ключе;
  - **2026-05-19 выгрузка скачком расширилась** (103 магазина вместо 99, 1 202 товара вместо 952, строк вдвое) —
    история до и после неоднородна, пока не выяснена причина;
  - сетка неполная: нет строки ≠ продаж 0.

## Текущее состояние кода

- Python 3.13, uv. `package = false`: проект — набор скриптов (`main.py` + `src/`),
  а не устанавливаемый пакет. Зависимости — `pandas`, `prefect`, `python-dateutil`,
  `python-dotenv`, `pyyaml`.
- **Пути и подключение — только через `src/lib/settings.py`**
  ([docs/architecture.md](docs/architecture.md), разд. 4.1). Он единственный читает
  `config.yaml` и `.env`. Остальной код делает `from settings import paths, config`
  и каталоги сам не собирает, в том числе от текущего каталога и от `__file__`.
  **В `settings.py` — только каталоги**: имена файлов и маски задаёт шаг, который их
  читает или пишет (источники могут меняться).
  В начале прогона — `paths.ensure()`. Новый каталог — ключ в `config.yaml` и поле в `Paths`.
- `src/lib/clickhouse.py` — обёртки `exec_local` / `exec_client` над clickhouse-local
  и clickhouse-client, подключение — `config.clickhouse` (из `.env`: `CH_HOST`, `CH_PORT`,
  `CH_USER`, `CH_PSWD`).
- `src/lib/logger.py` — лог в `paths.logs/YYYY_MM_DD.log`, в консоль — от WARNING.
- Модули из `src/lib/` подключаются через `sys.path.append(<корень>/src/lib)`, затем
  `from settings import paths`, `from logger import logger`, `import clickhouse`.
- `src/preprocessing/` — каталог под шаги подготовки данных; в git шагов пока нет
  (временные `*_tmp.*` не отслеживаются).
- `scripts/ch-server.sh start|stop|restart|status|log` — локальный ClickHouse
  (single binary в `/clickhouse`).
- `main.py`, `README.md` — пустые.
- git: `origin` — GitHub `KolesnikNatalia/demand-forecact`.
