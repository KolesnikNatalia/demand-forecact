## О проекте

**Исследовательский** проект: прогноз спроса в сети розничных магазинов на **продукцию
собственного производства** (группа `100 СОБСТВЕННОЕ ПРОИЗВОДСТВО`) со сроком годности
**1–5 дней**. Прогноз питает **автозаказ на производство**: сколько произвести и отгрузить
в каждый магазин. Полная постановка — [docs/project.md](docs/project.md).

- **Горизонт 7 дней, шаг — день**, объект — магазин × товар. Прогноз пересчитывается
  каждый день. Качество оценивать по каждому дню горизонта, а не по сумме за неделю.
  **Главные дни — 2–3**: по ним производство выпускает продукцию. Дни 5–7 нужны для
  закупа сырья.
- **Цели заказчика, на конец дня:**
  - **доступность** — 75–80% ассортимента магазина в наличии, достаточно 1–2 единиц;
  - **списания** — не более 5%;
  - **доступность топового ассортимента важнее хвоста.** Средняя доступность без разреза
    «топ / хвост» — неполный ответ.
- Как именно считать эти KPI (база списаний, правило «топа», наличие для весового товара),
  момент расчёта заказа и срок исполнения **пока не определены** — список в
  [docs/project.md](docs/project.md), разд. 7. Не додумывать: спрашивать, а решения
  записывать туда.
- Порядок работы: данные → **насколько они прогнозируемы** → модели **от простых к сложным**
  ([docs/research_plan.md](docs/research_plan.md)). Следующая ступень берётся, только если
  обыграла предыдущую по KPI на том же бэктесте. WAPE/MAPE — контрольные метрики, не целевые.

## Правила для любой модели и метрики

- **Ошибки обходятся по-разному.** Завысили — списание, занизили — пустая полка и потерянная
  продажа. Одной точки мало: заказ — это квантиль прогноза, доступность — покрытие этого
  квантиля. Поэтому квантили надо калибровать и проверять покрытием.
- **Продажи ≠ спрос.** В выгрузке 52% дней с продажами заканчиваются нулевым остатком:
  спрос в них цензурирован. Для оценки спроса такие дни восстанавливать или исключать.
  В метрике доступности они остаются: это и есть событие «товара не было».
- **Прогноз «из будущего» запрещён.** Признаки — только из того, что известно к моменту
  расчёта заказа. Факт продаж, остатки, списания после этого момента в признаки не попадают.
  Валидация — по времени (holdout / скользящее окно), без перемешивания.
- **`кг` и `шт` — разные распределения** (весовой товар дробный в 99.8% продаж,
  штучный целый всегда). Модели, калибровку и метрики вести раздельно, в одну цифру
  не сводить, `кг` в «штуки» не масштабировать.
- Ряды короткие и разреженные: 46% строк с нулевыми продажами, позиции появляются
  и выводятся. Учитывать при выборе модели и агрегации.

## Стек и архитектура

Подробно — [docs/architecture.md](docs/architecture.md). **Prefect и MLflow установлены,
но flow и логирования прогонов ещё нет.** Библиотеки ставит пользователь, когда до них
доходит работа (см. «Общие указания»).

- **Обработка и преобразование данных — SQL в ClickHouse** (`clickhouse-local` по parquet,
  `clickhouse-client` к серверу). Группировки, соединения, окна, признаки и проверки — в SQL,
  не в pandas.
- **Python — обёртка и обучение.** Шаг — модуль с `run(cfg, ...)`, SQL — в f-строке, параметры
  из конфига, запуск через `exec_local` → parquet. Тяжёлое режется на подшаги с промежуточным
  parquet. **Промежуточные файлы и файлы SQL-команд не удаляются** — по ним отслеживают
  результаты подшагов; Memory-таблицы вместо них не использовать. Модели читают готовые parquet.
- **Где что лежит: все данные шага — в каталоге своего слоя** (`prepared`, `features`,
  `forecast`, `analysis`, `checks`), включая промежуточные результаты подшагов.
  **`paths.tmp` — только файлы SQL-команд**, данные туда не пишутся.
- **Prefect — оркестратор.** Шаги пишутся обычными функциями и работают без Prefect,
  flow — тонкий слой поверх них. Проверки качества — отдельные задачи; error останавливает
  следующие шаги.
- **MLflow — эксперименты.** Каждый прогон бэктеста логирует params, metrics (KPI по веткам,
  калибровку, WAPE как контрольную), tags (git-коммит, отпечаток данных) и artifacts.
- **Качество данных — обязательная часть пайплайна**
  ([docs/data_quality.md](docs/data_quality.md)): тесты контракта сырья, тесты каждого
  слоя, проверка отсутствия утечки будущего, мониторинг дрейфа данных и прогноза. Проверка
  не чинит данные, а останавливает прогон или пишет warning.
- Грабли ClickHouse (Nullable из parquet, нематериализуемые CTE, `INTO OUTFILE` без каталогов
  и др.) — [docs/architecture.md](docs/architecture.md), разд. 8.

## Данные

- Сырые факты: `data/main_data/main_data_YYYY_MM.parquet`, 2025-01…2026-08, 11.8 млн строк,
  **строка = день × магазин × товар** (ключ уникален). В git не попадают.
- Читать `clickhouse-local` по маске `file('data/main_data/main_data_*.parquet')` или
  `exec_local` из `src/lib/clickhouse.py`; в коде — `paths.main_data / 'main_data_*.parquet'`.
- Схема, цифры и ловушки — [docs/data.md](docs/data.md). Самое важное:
  - **списаний и срока годности в данных нет** — KPI списаний сейчас считается только через прокси;
  - **`SalesByLevel*Qty` — продажи группы за тот же день в своей единице измерения**
    (пересчитаны 2026-09-18); в признаки — только с лагом. Любой новый групповой агрегат —
    с `ItemMeasure` в ключе;
  - **2026-05-19 выгрузка скачком расширилась** (103 магазина вместо 99, 1 202 товара вместо 952, строк вдвое).
    Разбор 2026-09-19: матрицу расширили на бумаге, выручка сети не изменилась, магазины
    не открывались. Большая часть добавленных пар — пустые ряды;
  - **пустые ряды** (за весь период ни продажи, ни ненулевого остатка; 8 634 пары, 20%)
    помечаются и в анализе не участвуют. У остальных пар жизнь — от первой до последней
    активности (остаток или продажа): матричные дни вне этого отрезка — пропуски, как дни
    вне матрицы;
  - сетка неполная: нет строки ≠ продаж 0. Выгрузка размножена на каждый день матрицы,
    строки «всё по нулям» есть только при `isMatrix = 1`: **долю нулей и всё, что опирается
    на нули (ADI, частота продаж, дефицит, доступность), считать только по матричным дням**.

## Текущее состояние кода

- Python 3.13, uv. `package = false`: проект — набор скриптов (`main.py` + `src/`),
  а не устанавливаемый пакет. Зависимости — `mlflow`, `pandas`, `prefect`,
  `python-dateutil`, `python-dotenv`, `pyyaml`.
- **Пути и подключение — только через `src/lib/settings.py`**
  ([docs/architecture.md](docs/architecture.md), разд. 4.1). Он единственный читает
  `config.yaml` и `.env`. Остальной код делает `from settings import paths, config`
  и каталоги сам не собирает, в том числе от текущего каталога и от `__file__`.
  **В `settings.py` — только каталоги**: имена файлов и маски задаёт шаг, который их
  читает или пишет (источники могут меняться).
  В начале прогона — `paths.ensure()`. Новый каталог — ключ в `config.yaml` и поле в `Paths`.
- `src/lib/clickhouse.py` — обёртки `exec_local` / `exec_client` над clickhouse-local
  и clickhouse-client, подключение — `config.clickhouse` (из `.env`: `CH_HOST`, `CH_PORT`,
  `CH_USER`, `CH_PSWD`).
- `src/lib/logger.py` — лог в `paths.logs/YYYY_MM_DD.log`, в консоль — от WARNING.
- `src/lib/params.py` — профиль параметров прогона (`profiles/*.yaml`): период, пороги,
  границы классов. Раздел берётся через `profile.section(имя, набор ключей)`, опечатка
  роняет прогон. Модуль назван `params`, а не `profile`: стандартный `profile`
  перекрыл бы его при `sys.path.append`.
- `src/lib/sql.py` — сборка SQL: `quoted`, `case`, `branch_case`, `scope_case`
  и `source_select` (выгрузка с обнулением возвратов и снятым `Nullable`).
- Модули из `src/lib/` подключаются через `sys.path.append(<корень>/src/lib)`, затем
  `from settings import paths`, `from logger import logger`, `import clickhouse`.
- `src/preprocessing/series_days.py` — этап 1 анализа рядов: `series_days.parquet`
  (день × пара с разметкой) и `series_arrays.parquet` (ряд массивом по дням жизни,
  пропуск — `NaN`) в слое `prepared`. В слой идут только единицы измерения из профиля:
  ряд без ветки в расчёт не попадает, а сколько строк так отсеяно — показывает warning.
- **Проверки — отдельный запуск, а не часть расчёта.** `uv run python src/preprocessing/series_days.py`
  считает слой; `--checks` считает и проверяет; `--checks-only` проверяет уже посчитанное.
  Проверки читают выгрузку ещё раз, поэтому в регулярном расчёте и экспериментах
  их не гоняют — только на новой выгрузке, новом профиле или после правки шага.
- `src/checks/series_checks.py` — сами проверки. Журнал прогона — `data/checks/series_days_checks_<время>.parquet`,
  рядом отчёт `.md`: сверху замечания и ошибки, ниже таблица всех проверок; тот же список
  уходит в лог одним блоком в конце. Строки идут error → warning → ok.
- **Останавливает расчёт только беда всего слоя** (дубль ключа, разошедшиеся суммы,
  пустой слой). Проблема отдельных позиций — warning в отчёт: из-за одной SKU нельзя
  оставить без расчёта всю сеть.
- `tests/` — фикстура выгрузки (`fixtures.py`, 3 магазина × 5 товаров × 14 дней)
  и тесты шага; запуск — `uv run pytest` (pytest в группе `dev`). Тест берёт свои
  каталоги через `settings.load(<свой config.yaml>)` и рабочие данные не трогает.
- `scripts/ch-server.sh start|stop|restart|status|log` — локальный ClickHouse
  (single binary в `/clickhouse`).
- `main.py`, `README.md` — пустые.
- git: `origin` — GitHub `KolesnikNatalia/demand-forecact`.

## Требования и планы (`prd/`)

Работа над фичей идёт по цепочке скиллов:

1. `prd` → `prd/prd-<name>.md` — что и зачем, критерии готовности. Как реализовывать,
   в PRD не пишется.
2. `plan-prd` → `prd/plan-<name>.md` — этапы реализации: каждый даёт рабочий результат,
   в этапе не больше пяти задач, тесты запланированы там, где их можно написать. План
   покрывает все критерии готовности PRD и не добавляет задач сверх него.
3. `issues` → milestone на этап и issue на задачу в GitHub (`origin`).

В `docs/` лежат постановка и результаты, в `prd/` — требования к фичам и планы работ.
Выполненную задачу отмечать `[x]` в плане. Когда фича сделана, её выводы переносятся в `docs/`.

## Окружение

- Менеджер пакетов — **uv**. Зависимости ставит **пользователь** (`uv add <пакет>`, не
  `pip install`), по мере надобности, заранее не ставить. Окружение `.venv` в `.gitignore`.
- **Агент запускает код через `uv run <команда>`.** `uv.lock` агент не правит — ни руками,
  ни командами. Если `uv run` собирается перезаписать lock (пользователь поменял
  зависимости и ещё не синхронизировал), запускать `uv run --frozen` и сказать об этом
  пользователю.
- Локальная среда — WSL (Linux).

## Общие указания

- **Библиотеки устанавливает только пользователь. Агенту ставить их запрещено** — любые,
  любым способом: `uv add` / `uv remove` / `uv sync` / `uv pip install`, `pip install`,
  `uvx` / `pipx`, `uv tool install`, `apt`, `npm` и т. п. Зависимости в `pyproject.toml`
  и `uv.lock` тоже не правит. Нужна библиотека — назвать её, объяснить зачем, дать команду
  для установки и дождаться, пока пользователь поставит. Для документации это же правило:
  в планах и PRD установка — шаг пользователя, а не агента.
- Коммитит агент только по явной просьбе пользователя, через скилл `commit`. Пушит — только
  по указанию пользователя. Подписей агента (`Co-Authored-By`, «Generated with Claude Code»)
  в коммитах и заметках не ставить.
- Секреты (пароли, ключи, строки подключения) — не в код и не в git; держать в `.env`
  (он уже в `.gitignore`); список ключей — в шаблоне `.env.example`, его обновлять вместе с `.env`.
- Язык документации, комментариев и коммитов — русский.
