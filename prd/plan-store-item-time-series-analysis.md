# Plan: Анализ временных рядов «магазин × товар»: прогнозируемость и закономерности

**PRD:** [prd-store-item-time-series-analysis.md](prd-store-item-time-series-analysis.md)
**Дата:** 2026-09-19

## Этапы реализации

### Этап 1: Подготовка дневных рядов

**Цель:** Дневной ряд каждой пары с разметкой, на которой держится весь анализ: ветка,
матричный день, день дефицита, два варианта ряда, когорта. Плохие данные останавливают
расчёт до анализа.
**Затрагивает:** предобработка (SQL-шаг в `src/preprocessing/` → parquet), параметры
анализа, проверки качества, тесты.
**Задачи:**

- [ ] Профиль параметров анализа `profiles/series_analysis.yaml`: период, дата когорты
      (2026-05-19), список спорных подгрупп, порог наличия ветки (`шт` — 1, `кг` — 0.1).
      Следующие этапы дописывают свои параметры сюда же. Каталог результатов анализа —
      ключ в `config.yaml` и поле в `Paths`.
- [ ] SQL-шаг `run(cfg)`: строка «день × пара» с веткой `кг` / `шт`, флагом матричного дня,
      флагом дефицита (матричный день с вечерним остатком ниже порога наличия ветки),
      значением ряда в двух вариантах («продажи как есть»; «спрос без дефицита» — день
      дефицита пуст) и атрибутами пары: подгруппа, подподгруппа, сеть, формат, когорта.
      Возвраты (отрицательные продажи) обнуляются вместе с выручкой, строка остаётся.
      Флаг пустого ряда — у пары за весь период ни продажи, ни ненулевого остатка.
      Дальше такие пары в расчётах не участвуют. Первый и последний день активности
      пары: матричные дни вне этого отрезка — пропуски, как дни вне матрицы. Когорта —
      по первому дню активности: «до» или «после» даты из профиля. Флаг магазина,
      выбивающегося из общей массы (правило — в профиле).
- [ ] Проверки уровня error, которые останавливают расчёт: ключ «день × пара» уникален;
      продажи и выручка по ветке равны сырью с тем же обнулением возвратов; у каждой
      строки ровно одна ветка. Число обнулённых возвратов — warning.
- [ ] pytest ставит пользователь (`uv add --dev pytest`); фикстура в `tests/` — 3 магазина × 5 товаров × 14 дней:
      дефицит, остаток `кг` между 0 и 0.1 кг, возврат, продажа вне матрицы, пара без
      матричных дней, пустой ряд, пара с матричными днями до первой и после последней
      активности, `кг` и `шт` в одной подподгруппе, пара, появившаяся после даты когорты.
- [ ] Тесты: разметка матричных дней, дефицита, вариантов ряда и когорты совпадает
      с ручной; дубль ключа, расхождение сумм и строка без ветки останавливают шаг.

**Когда готов:** на полной выгрузке шаг пишет parquet и проходит проверки; тесты зелёные;
на испорченной фикстуре шаг падает с понятной ошибкой.

### Этап 2: Профиль рядов: история, класс спроса, дефицит, ABC

**Цель:** Профиль — одна строка на пару и вариант ряда. Его можно фильтровать по ветке,
подгруппе и ABC-классу (первый сценарий PRD, пока без классов прогнозируемости).
**Затрагивает:** расчёт профиля (SQL → parquet в слое анализа), проверки качества, тесты.
**Задачи:**

- [ ] История и атрибуты: длина жизни, дни в матрице, уровень продаж, выручка, доля
      выручки вне матрицы, средняя цена `SalesAmount / SalesQty` по дням с продажами.
- [ ] По матричным дням — класс спроса (доля дней с продажами, доля нулей, ADI, CV²,
      квадрант Syntetos–Boylan) и дефицит (доля дней дефицита, доля продаж в такие дни). У пар без матричных дней — «неприменимо».
- [ ] ABC-классы, 3 основания × 2 уровня: выручка, количество (внутри ветки), частота
      продаж (по матричным дням) — по магазину и по магазину внутри `ItemIdLevel2`.
      Пороги — в профиле параметров, по умолчанию 80 / 15 / 5%.
- [ ] Сборка профиля и проверки уровня error: ключ «пара × вариант» уникален, все пары
      выгрузки на месте, продажи и выручка по ветке равны сырью, у каждой непустой пары
      заполнены ветка, подгруппа, когорта, класс спроса, доля дефицита и шесть ABC-классов.
      У пустых рядов стоит флаг и «неприменимо», в ABC и сводках они не участвуют.
- [ ] Тесты на фикстуре: ADI, CV², квадрант и ABC-классы совпадают с ручным расчётом;
      доля нулей и ADI, пересчитанные по всем строкам, дают другое число, чем по
      матричным дням; пара без матричных дней получает «неприменимо».

**Когда готов:** профиль посчитан на полной выгрузке, проверки проходят, тесты зелёные.

### Этап 3: Каркас отчёта

**Цель:** `docs/series_analysis.md` с датой, отпечатком данных и первым разделом.
Построитель сводных таблиц, на котором строятся все следующие разделы, не даёт смешать
ветки и подмешать спорные подгруппы в итоги.
**Затрагивает:** отчёт (Python: таблицы и графики из parquet), тесты.
**Задачи:**

- [ ] Построитель сводных таблиц: ветка всегда в ключе разреза, спорные подгруппы —
      отдельной строкой и вне основных итогов. Таблица без ветки в ключе — ошибка.
- [ ] Шапка отчёта: дата расчёта и отпечаток данных (период, число строк); пересчитываются
      при каждом прогоне.
- [ ] Раздел «Популяция»: число пар и доля выручки по веткам, когортам и спорным
      подгруппам; класс спроса и доля дефицита в двух вариантах ряда; число и доля
      выручки пар с «неприменимо».
- [ ] Тесты построителя: таблица без ветки падает, строка спорных подгрупп есть,
      в основной итог они не входят.

**Когда готов:** отчёт собирается из профиля одной командой, в нём дата, отпечаток
и раздел «Популяция»; тесты зелёные.

### Этап 4: Граница возможного

**Цель:** Ответ, достижимы ли 75–80% доступности при остатке не выше 5% хотя бы в пределе
и в каком сегменте. Это верхняя оценка: лучше не сделает ни одна модель.
**Затрагивает:** расчёт (SQL → parquet в слое анализа), отчёт, тесты.
**Задачи:**

- [ ] Для каждого `q` из сетки профиля параметров (по умолчанию 0.4, 0.5, …, 0.9, 0.95)
      заказ = квантиль `q` собственного распределения ряда, посчитанный с подглядыванием
      в будущее. По матричным дням — доступность на конец дня и вечерний остаток как доля
      выпуска, для обоих вариантов ряда. Подглядывание помечено в данных и в отчёте.
- [ ] Фактическая точка по истории: текущие доступность и остаток теми же определениями.
      Наличие — остаток не ниже порога наличия ветки из профиля (тот же порог, что для
      дефицита на этапе 1).
- [ ] Разрезы: ветка × ABC-класс (по каждому из шести правил) × вариант ряда; отдельно
      подгруппа и формат магазина.
- [ ] Раздел отчёта: при каком `q` и каком остатке достигаются 75% и 80% доступности,
      отдельно для топа и хвоста каждой ветки. Выводы по `кг` помечены условными, остаток —
      верхняя оценка списаний.
- [ ] Тесты на фикстуре: доступность и остаток при заданном `q` совпадают с ручным
      расчётом; дни вне матрицы в доступность не входят.

**Когда готов:** кривые «доступность / остаток» по сетке `q` с фактической точкой есть
во всех разрезах; отчёт прямо отвечает про 75% и 80% для топа и хвоста; тесты зелёные.

### Этап 5: Меры прогнозируемости: реализация и контрольные тесты

**Цель:** Проверенный модуль мер по одному ряду: каждая мера на ряде с известным ответом
даёт контрольное значение.
**Затрагивает:** расчёт мер (Python-модуль; нужные библиотеки ставит пользователь), тесты.
**Задачи:**

- [ ] Меры ритма и спектра: сила недельного ритма, ACF на лагах 1 и 7, эффективный порядок
      PACF, спектральная энтропия и ForeCA Ω, доля недельных гармоник, VR(7), показатель
      Хёрста.
- [ ] Меры сложности и перемешивания: перестановочная энтропия со сложностью
      Йенсена–Шеннона, SampEn и многомасштабная энтропия, граница Πmax, η Кабудана для
      SeasonalNaive и Naive.
- [ ] Правила применимости: минимальная длина ряда для каждой меры (параметр профиля),
      обработка пропусков — дней вне матрицы и дней дефицита. Мера, которой нужен
      непрерывный ряд, на ряде с пропусками даёт «неприменимо», а не число.
- [ ] Тесты: каждая мера на синусоиде и белом шуме даёт контрольное значение (формулы
      и примеры — [wiki/predictability_and_classification_plan.md](../wiki/predictability_and_classification_plan.md));
      короткий ряд и ряд с пропусками дают «неприменимо».

**Когда готов:** все меры из списка PRD реализованы, тесты на рядах с известным ответом
проходят.

### Этап 6: Калибровка мер на суррогатах

**Цель:** Понять, что каждая мера меряет при нашей доле нулей — структуру или
разреженность. Вердикт по мере выносится до сверки с ошибкой.
**Затрагивает:** расчёт мер (Python), отчёт, тесты.
**Задачи:**

- [ ] Генератор суррогатов: белый шум, недельная сезонность, сезонность с шумом, тренд,
      AR(1), случайное блуждание, прерывистый спрос, редкие всплески; доля нулей 0–0.9;
      маска случайная и блочная (имитация дефицита). Сетка и число реализаций — в профиле
      параметров.
- [ ] Тест генератора: фактическая доля нулей равна заданной, блочная маска даёт блоки,
      случайная — нет.
- [ ] Таблица «мера × семейство × доля нулей × маска» → parquet в слое анализа.
- [ ] Вердикт по каждой мере — оставлена, ограничена по применимости или исключена —
      по критерию «при доле нулей 0.8 сезонность отличается от шума с эффектом не меньше
      1σ». Ограничения переходят в правила применимости модуля мер.
- [ ] Раздел отчёта с таблицей калибровки и вердиктами; фиксируется до начала этапа 9.

**Когда готов:** таблица калибровки построена, у каждой меры записан вердикт, раздел
отчёта зафиксирован.

### Этап 7: Меры на рядах выгрузки

**Цель:** Меры прогнозируемости и флаги применимости в профиле. Видно, какую долю
«непрогнозируемости» создали наши же дефициты.
**Затрагивает:** расчёт мер по рядам слоя этапа 1, профиль, отчёт, тесты.
**Задачи:**

- [ ] Стратифицированная подвыборка для мер с квадратичной стоимостью; проверка:
      представлены все ячейки «квадрант × ветка».
- [ ] Расчёт мер, не исключённых на этапе 6, по паре и варианту ряда: матричные дни,
      пропуски остаются пропусками. Флаг применимости каждой меры (длина, вердикт
      суррогатов, пропуски; нет матричных дней — «неприменимо»).
- [ ] Меры и флаги — в профиль; проверки уровня error: ключ по-прежнему уникален, флаг
      заполнен у каждой пары для каждой меры.
- [ ] Раздел отчёта: по каждой мере — число неприменимых пар и их доля выручки ветки;
      разница мер между вариантами «продажи как есть» и «спрос без дефицита».
- [ ] Тест: на фикстуре мера из шага совпадает с расчётом модуля по тому же ряду,
      пропуски доходят до модуля пропусками, а не нулями.

**Когда готов:** профиль дополнен мерами и флагами на полной выгрузке, проверки и тест
проходят, раздел отчёта есть.

### Этап 8: Простые прогнозы и их ошибка

**Цель:** Ошибка опорных прогнозов по каждой паре и каждому дню горизонта — эталон,
с которым сверяются меры.
**Затрагивает:** прогнозирование (опорные модели), проверки качества, тесты.
**Задачи:**

- [ ] Отложенное по времени окно: начало и длина — в профиле параметров. Прогноз строится
      каждый день окна на дни горизонта 1–7, данные — только до дня расчёта. Опорные
      прогнозы по предыдущим 91 дню (длина истории — параметр профиля): среднее, медиана
      и медиана по дню недели.
- [ ] Ошибка по паре × варианту ряда × модели × дню горизонта: WAPE и pinball loss
      (квантили — эмпирические квантили тех же 91 дня) → parquet в слое анализа.
      В сводке выделены дни 2–3 (выпуск) и 5–7 (закуп сырья).
- [ ] Проверка уровня error: все даты, из которых собран каждый прогноз, раньше его дня
      расчёта.
- [ ] Тесты: прогнозы и ошибки на фикстуре совпадают с ручным расчётом; изменение данных
      в день расчёта и позже не меняет прогноз.

**Когда готов:** таблица ошибок по дням горизонта 1–7 посчитана на полной выгрузке,
проверка на утечку и тесты проходят.

### Этап 9: Связь мер с фактической ошибкой

**Цель:** Какие меры отделяют ряды с большой ошибкой простого прогноза от рядов с малой
внутри класса спроса, а не за счёт разреженности.
**Затрагивает:** анализ (Python по профилю и таблице ошибок), отчёт, тесты.
**Задачи:**

- [ ] Для каждой оставленной меры по каждой ветке: взвешенная по объёму ранговая
      корреляция с ошибкой и децильная таблица. Основная — ошибка на днях горизонта 2–3,
      отдельно — на днях 5–7.
- [ ] Разделение ошибки внутри квадранта спроса своей ветки и вердикт по мере. Если
      не разделяет ни одна мера, это записывается как результат.
- [ ] Корреляции между мерами: из групп сильно коррелирующих остаётся одна (порог —
      в профиле параметров).
- [ ] Тест: взвешенная ранговая корреляция и децили на маленьком примере совпадают
      с ручным расчётом.
- [ ] Раздел отчёта: корреляции, децильные таблицы, вердикты и итоговый набор мер.

**Когда готов:** у каждой оставленной меры по каждой ветке есть корреляция, децильная
таблица и вердикт; итоговый набор мер записан в отчёте.

### Этап 10: Классы прогнозируемости

**Цель:** Каждой паре — класс и решение по моделированию: где нужен прогноз, а где хватит
правила запаса.
**Затрагивает:** анализ, профиль, проверки качества, отчёт.
**Задачи:**

- [ ] Классы по каждой ветке из мер, прошедших этап 9 (например, «структуры нет»,
      «уровень», «календарь», «сложный сигнал»). Границы подбираются по данным.
- [ ] Для каждого класса — решение: не моделировать (правило запаса), простая модель,
      календарная модель или отдельное моделирование; доля пар и выручки.
- [ ] Класс — в профиль; у пар с недостаточной историей — «неприменимо». Проверка:
      у каждой пары с достаточной историей класс есть, каждый класс держит не меньше 3%
      выручки ветки.
- [ ] Раздел отчёта: классы с решениями; доля выручки ветки на прогнозируемых рядах
      и на рядах без структуры, отдельно для топа и хвоста.
- [ ] Тест: проверка классов падает, если класс держит меньше 3% выручки ветки или у пары
      с достаточной историей нет класса.

**Когда готов:** профиль фильтруется по классу прогнозируемости, проверка классов
проходит, раздел отчёта есть.

### Этап 11: Закономерности: календарь, жизненный цикл и тренд

**Цель:** Какие календарные эффекты осмысленны для моделей; как ряды появляются, выходят
на уровень и меняются, в том числе после 2026-05-19.
**Затрагивает:** справочник календаря, анализ (SQL-агрегаты + Python), отчёт, тесты.
**Задачи:**

- [ ] Справочник производственного календаря РФ на 2025–2026: праздники и предпраздничные
      дни. Тест: справочник покрывает весь период выгрузки.
- [ ] Раздел «Календарь»: доля рядов со значимым недельным ритмом; профиль дня недели
      по подгруппам и форматам; праздники, предпраздничные дни, начало и конец месяца —
      против того же дня недели в обычные недели; январь–август 2025 против 2026.
- [ ] Раздел «Жизненный цикл и тренд», часть 1: длительность жизни пар; ввод и вывод
      позиций, переходы `isMatrix`; длина стартового периода новой пары до выхода
      на устойчивый уровень.
- [ ] Раздел «Жизненный цикл и тренд», часть 2: доля рядов со значимым трендом,
      структурные сдвиги; изменились ли уровень и доля нулей у пар, существовавших
      до 2026-05-19.
- [ ] Тесты на синтетических рядах: недельный ритм, тренд и сдвиг находятся там, где
      заложены, и не находятся на шуме; длина стартового периода совпадает с заложенной.

**Когда готов:** в отчёте оба раздела с цифрами по веткам на все пункты PRD, тесты
проходят.

### Этап 12: Закономерности: дефициты и связи между рядами

**Цель:** Сколько продаж приходится на дни распродажи и как ряды влияют друг на друга:
общий день магазина, замещение, цена.
**Затрагивает:** анализ (SQL-агрегаты + Python), проверки качества, отчёт, тесты.
**Задачи:**

- [ ] Раздел «Дефициты» (матричные дни): частота дней дефицита по ветке, ABC-классу и дню
      недели; доля продаж, пришедшаяся на дни распродажи; как дефицит меняет меры
      прогнозируемости (по итогам этапа 7).
- [ ] Раздел «Связи между рядами», часть 1: сходство профиля одного товара в разных
      магазинах; доля вариации ряда, объясняемая общим днём магазина и подгруппы.
      Групповые агрегаты — с `ItemMeasure` в ключе. Своды `SalesByLevel*Qty` того же дня —
      только для описания; вывод о пригодности как признака — только для лагированной
      версии.
- [ ] Раздел «Связи между рядами», часть 2: замещение внутри подподгруппы — продажи позиции
      в дни дефицита соседней против обычных дней.
- [ ] Раздел «Связи между рядами», часть 3: реакция продаж на изменение средней цены
      у рядов, где цена менялась.
- [ ] Тесты на фикстуре: доля продаж в дни распродажи и эффект замещения совпадают
      с ручным расчётом; групповой агрегат с `кг` и `шт` в одной подподгруппе не складывает
      ветки.

**Когда готов:** в отчёте оба раздела с цифрами по веткам на все пункты PRD, тесты
проходят.

### Этап 13: Сравнение правил топа

**Цель:** Насколько шесть правил ABC расходятся и меняют ли выводы о прогнозируемости
и границе возможного. Итоговое правило выбирает заказчик.
**Затрагивает:** анализ (SQL → parquet), отчёт, тесты.
**Задачи:**

- [ ] Пересечение классов A между правилами, по каждой ветке.
- [ ] Согласованность класса одного товара в разных магазинах.
- [ ] Устойчивость класса по кварталам: ABC по каждому кварталу и переходы между
      классами.
- [ ] Ответ в отчёте: меняются ли выводы о прогнозируемости (этап 10) и о границе
      возможного (этап 4) от выбора правила.
- [ ] Тест: пересечение, согласованность и устойчивость на фикстуре совпадают с ручным
      расчётом.

**Когда готов:** три таблицы сравнения есть в отчёте, ответ про влияние правила на выводы
записан, тест проходит.

### Этап 14: Итоговый отчёт и перезапуск на новой выгрузке

**Цель:** Отчёт с выводами для перехода к моделям; анализ пересчитывается на новой
выгрузке без правки кода.
**Затрагивает:** запуск анализа, проверки качества, отчёт, документация (`docs/`).
**Задачи:**

- [ ] Выводы для перехода к моделям: лаги и календарные эффекты, сегменты для раздельного
      моделирования, ряды, где хватит правила запаса.
- [ ] Проверка всех сводных таблиц отчёта: ни одна не складывает `кг` и `шт`, спорные
      подгруппы идут отдельной строкой и не входят в основные итоги.
- [ ] Одна точка запуска всего анализа по профилю параметров (без Prefect): период,
      пороги, сетка `q` и пороги ABC — только в профиле. Прогон с другим периодом проходит
      без правки кода; нарушение ключа, сумм или смешение веток его останавливают.
- [ ] Решения, меняющие постановку, — в [research_plan.md](../docs/research_plan.md)
      (этап 1) и [project.md](../docs/project.md) (разд. 7); ссылка на отчёт — в таблице
      документации `CLAUDE.md`.

**Когда готов:** отчёт датирован, в нём отпечаток данных и выводы для моделей; все
критерии готовности PRD отмечены; прогон с другим периодом проходит без правки кода.
