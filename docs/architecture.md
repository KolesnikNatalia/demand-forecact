# Архитектура и стек

> Целевое устройство, зафиксировано 2026-09-18. **Prefect и MLflow установлены, но flow
> и логирования прогонов ещё нет:** библиотеки ставит пользователь (`uv add`), когда до них
> доходит работа. Что уже решено — разделы 1–6, что предложено — раздел 7, что открыто — раздел 9.

## 1. Стек

| слой | инструмент | роль |
|---|---|---|
| обработка и преобразование данных | **ClickHouse**: `clickhouse-local` по parquet, `clickhouse-client` к серверу | вся подготовка — SQL: очистка, плотная сетка, агрегаты, признаки, проверки качества |
| обёртка | **Python** | собирает SQL из параметров конфига, запускает, передаёт файлы между шагами, логирует |
| обучение и прогноз | **Python** | модели, бэктест, метрики; вход — parquet, подготовленные ClickHouse |
| оркестрация | **Prefect** | цепочки шагов, зависимости, повторы, расписание, журнал запусков |
| эксперименты | **MLflow** | параметры, метрики, артефакты и модели каждого прогона, сравнение экспериментов |
| качество данных | SQL-проверки + Python | тесты данных на каждом слое и мониторинг дрейфа — [data_quality.md](data_quality.md) |

**Работа с данными — в ClickHouse, модели — в Python.** Группировки, соединения и оконные
функции по 11.8 млн строк считает ClickHouse. В Python попадает уже подготовленная выборка
того размера, который нужен модели.

## 2. Поток данных

```
data/main_data/*.parquet      сырые факты: день × магазин × товар
        │   проверки сырья (контракт выгрузки)          ── error → стоп
        ▼
prepared    плотная сетка, очистка, ветка кг/шт,          SQL → parquet
            флаг дефицита, разметка топа
        │   проверки слоя: сетка, суммы, ветки
        ▼
features    признаки на момент расчёта заказа             SQL → parquet
        │   проверка: нет данных позже момента расчёта
        ▼
models      бэктест, обучение, прогноз квантилей          Python + MLflow
        ▼
order       заказ = квантиль прогноза на уровне сервиса сегмента
        ▼
monitoring  дрейф данных, калибровка, KPI против факта
```

Каждый слой — parquet в своём каталоге `data/<слой>/`. **Все данные шага лежат в каталоге
своего слоя, включая промежуточные:** результат подшага — такие же данные, и искать их
надо там же, где остальные (решение 2026-09-20). В `data/tmp/` — **только файлы
SQL-команд**. В git ничего из этого не хранится и после шага **не удаляется**: по файлам
отслеживают промежуточные результаты (решение 2026-09-19). Следующий прогон их перезаписывает.

## 3. Как устроен шаг обработки данных

Образец — скрипты `/work/projects/forecast/preprocessing/etl/` (прежде всего
`op_train_data.py`). Это проект, из которого пришла `wiki/`. Смотреть его можно только
на чтение и только как образец приёмов. Пути, данные и конфиги оттуда не переносить.

- **Модуль — один логический шаг** с точкой входа `run(cfg, ...)`. Функция возвращает
  пути к результатам, чтобы следующий шаг брал их, а не угадывал.
- **SQL живёт в функциях модуля** как f-строка. Период, списки единиц и пороги приходят
  из конфига. Списки значений для `IN (...)` экранируются хелпером, а не подставляются
  как есть.
- **Выполнение — `exec_local(command, command_file, save_file, 'Parquet')`** из
  [src/lib/clickhouse.py](../src/lib/clickhouse.py). Функция пишет запрос в файл команды,
  дописывает `INTO OUTFILE ... FORMAT Parquet` и вызывает `clickhouse-local --queries-file`.
  Если нужен сервер ClickHouse, та же схема работает через `exec_client`.
- **Тяжёлый расчёт режется на подшаги с промежуточным parquet.** Например:
  пары → групповые агрегаты → плотная сетка → раскладка train / valid / test.
  CTE в ClickHouse не материализуются, поэтому общий кусок лучше один раз сохранить
  в файл. Промежуточный результат — всегда файл, а не Memory-таблица внутри одного
  запуска: файл остаётся на диске, и подшаг можно проверить отдельно. Кладётся он
  в каталог своего слоя (`prepared`, `analysis`, `checks`), а не в `tmp`: в `tmp`
  лежат только файлы SQL-команд.
- **Проверки — отдельные запросы и отдельный запуск** (решение 2026-09-20). Шаг считает
  слой, проверки читают готовые файлы. Регулярный расчёт и эксперименты гоняют шаг часто,
  а проверки ещё раз перечитывают выгрузку, поэтому по умолчанию они не выполняются:
  их включает ключ `--checks` (посчитать и проверить) или `--checks-only` (проверить
  уже посчитанное). В Prefect это будет отдельная задача. Нарушение контракта —
  исключение с понятным текстом. Дубль нельзя «сгладить» через `max()` в SQL:
  по значению не видно, какая строка верная.
- **Параметры запроса `--param_*` рассмотрены и отклонены** (решение 2026-09-20).
  Значения подставляются в f-строку, списки и литералы — через хелперы `src/lib/sql.py`.
  f-строка показывает готовый текст запроса — его видно в коде и в файле команды
  рядом с результатом, а с параметрами пришлось бы держать в голове ещё и их значения.
- В лог пишутся время каждого запроса и путь к результату.

Из образца **не переносим**: абсолютные пути и даты, захардкоженные в коде, чтение
`config.yaml` от текущего каталога, `.bak`-копии файлов (история правок — в git).

## 4. Python

- **Обёртка.** Берёт пути и подключение из [src/lib/settings.py](../src/lib/settings.py),
  запускает шаги, пишет лог через [src/lib/logger.py](../src/lib/logger.py).
- **Обучение.** Модели читают parquet слоя `features` и пишут прогноз в parquet.
  Всё, что влияет на результат, попадает в MLflow.
- **Параметры — в конфигах, не в коде.** Эксперимент однозначно задают три вещи:
  конфиг, версия кода (git-коммит) и версия данных (период, отпечаток файлов).

### 4.1 Настройки и пути

Сделано 2026-09-18.

| файл | что хранит | в git |
|---|---|---|
| [config.yaml](../config.yaml) | пути: корень данных, каталоги слоёв, логи | да |
| `.env` | подключение к ClickHouse (`CH_*`), машинные переопределения (`DF_DATA_DIR`) | нет |
| [.env.example](../.env.example) | шаблон `.env`: ключи без значений | да |
| [src/lib/settings.py](../src/lib/settings.py) | единственный модуль, который читает оба файла; отдаёт неизменяемые датаклассы | да |

Использование в шаге:

```python
from settings import paths

paths.ensure()  # в начале прогона: проверить сырьё, создать каталоги результатов
command = f"select ... from file('{paths.main_data / 'main_data_*.parquet'}')"
clickhouse.exec_local(command, paths.tmp / 'grid.tmp', paths.prepared / 'grid.parquet', 'Parquet')
```

Правила:

- **Конфиг и `.env` читает только `settings.py`.** Остальной код импортирует `paths`
  или `config` и каталоги не собирает сам.
- **В `settings.py` только каталоги, без имён файлов и масок.** Имя файла задаёт шаг,
  который его читает или пишет: источники могут меняться, а каталоги остаются.
- **Корень проекта — от `__file__`, а не от текущего каталога**, поэтому скрипт можно
  запускать откуда угодно, в том числе из Prefect.
- **Относительный путь считается от корня** (каталоги слоёв — от корня данных),
  абсолютный берётся как есть.
- **Приоритет: переменная окружения → `.env` → `config.yaml`.** `DF_DATA_DIR`
  переносит все слои на другой диск или сервер без правки конфига.
- **При загрузке проверяется состав ключей:** опечатка в имени ключа — ошибка с
  перечнем недостающих и лишних, а не молчаливый путь по умолчанию.
- **Существование каталогов проверяет `paths.ensure()`**, а не импорт. Модуль можно
  импортировать и там, где данных нет: в тестах, в служебных скриптах.
- **Датаклассы неизменяемые** (`frozen`): поменять путь во время прогона нельзя.
- **Новый слой** — ключ в `paths.layers` конфига и поле в `Paths`. Без поля загрузка
  упадёт на лишнем ключе.
- **Тесты** вызывают `load(свой_config.yaml)` с временными каталогами и не трогают
  рабочие данные.
- **Параметры экспериментов** (период, модель, `q`) сюда не входят — у них будут
  свои профили.

## 5. Prefect — оркестрация

- **Task — один шаг:** ETL-шаг, набор проверок, обучение, бэктест или прогноз.
  **Flow — цепочка шагов.**
- **Шаги пишутся без Prefect** — обычными функциями `run(...)`. Flow — тонкий слой
  поверх них. Шаг должен запускаться и без оркестратора: при отладке, в тестах,
  в ноутбуке.
- **Проверки качества — отдельные задачи.** Ошибка уровня error останавливает
  следующие шаги.
- **Повторы при ошибке (`retries`)** — только для обращений к серверу ClickHouse и
  другим внешним источникам. Запрос `clickhouse-local` по файлу повторять незачем:
  он упадёт так же.
- Flow два вида:
  - **исследовательский** — подготовка данных → бэктест эксперимента → запись в MLflow;
  - **регулярный** — свежие данные → проверки → прогноз → заказ → мониторинг дрейфа.
    Расписание зависит от момента расчёта заказа, а он пока не определён
    ([project.md](project.md), разд. 7).

## 6. MLflow — эксперименты

**Run — один прогон бэктеста одной модели с одним конфигом. Experiment — вопрос или
ступень исследования** («baseline», «nb-glm», «lightgbm-quantile»), а не отдельная модель.

| что | содержимое |
|---|---|
| params | модель и гиперпараметры, уровень `q`, период данных, окна бэктеста, горизонт, ветка `кг`/`шт` |
| metrics | целевые: доступность (общая и топа), остаток — прокси списаний; калибровка: покрытие по сетке `q`, pinball loss; контрольные: WAPE, BIAS. Всё — раздельно по веткам |
| tags | git-коммит, отпечаток данных (период, число строк, хеш списка файлов), ступень исследования |
| artifacts | конфиг, таблицы метрик в разрезах (шаг горизонта, топ / хвост, формат), графики калибровки, отчёт проверок данных, прогноз |

- Метрики по шагу горизонта и по сегментам — таблицей-артефактом. В metrics
  выносится только то, по чему сравниваются прогоны.
- Прогоны сравнимы, только если у них одинаковые окна бэктеста и одна популяция
  рядов. Окна фиксируются один раз и между экспериментами не меняются.
- Модель, прошедшая в следующую ступень исследования, регистрируется в Model Registry.

## 8. Грабли ClickHouse

Собраны в образце на тех же данных. Каждый пункт уже стоил кому-то упавшего запроса.

- **`INTO OUTFILE` не создаёт каталоги** — создавать их до запуска.
- **`exec_local` / `exec_client` удаляют `save_file` перед запуском.** Упавший шаг
  оставляет не старый файл, а отсутствие файла. Следующий шаг должен падать,
  а не читать пустоту.
- **CTE не материализуются.** Упомянутый трижды считается трижды — тяжёлое выносить
  в промежуточный parquet.
- **`Nullable` из parquet ломает функции высшего порядка.** Строковые колонки выгрузки
  объявлены `Nullable` — снимать это во вложенном `select` (`ifNull`, `assumeNotNull`).
- **Вложенные лямбды ненадёжны** — разворачивать их в явный список.
- **`AMBIGUOUS_IDENTIFIER` указывает на `ON`, а виноват список выборки.**
  Присоединяемый CTE не должен отдавать имён, которые уже есть слева.
- **Алиас из списка выборки перекрывает исходную колонку в `WHERE`.** Источник читать
  через алиас таблицы (`src.ItemMeasure`).
- `exec_local` — для запросов к файлам, `exec_client` — для запросов к серверу.

Схемы таблиц, запросы и настройки ClickHouse сверять со скиллом
`clickhouse-best-practices`.
