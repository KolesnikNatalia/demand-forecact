# Качество данных: тесты и дрейф

> Зафиксировано 2026-09-18. Проект исследовательский, но пайплайн строится как для
> реального. Плохие данные должны останавливать расчёт до модели. Изменения в данных
> надо замечать раньше, чем они испортят заказ. Инструменты пока не установлены.

## 1. Принципы

- **Проверка — SQL-запрос в ClickHouse**, там же, где лежат данные. Python собирает
  результаты, решает, останавливать ли прогон, и пишет отчёт. Тянуть 11.8 млн строк
  в pandas ради проверки — дорого и незачем.
- **У каждой проверки есть уровень:**
  - **error** — сломан контракт (дубль ключа, пропал день, нет колонки). Прогон
    останавливается;
  - **warning** — данные странные, но расчёт возможен (отрицательные продажи, новая
    единица измерения). Факт уходит в отчёт и лог, прогон идёт дальше.
- **Проверка не чинит данные.** Нашла дубль — остановила прогон. Исправление делается
  в шаге, который эти данные породил, а не маскируется ниже по потоку.
- **Результаты хранятся с историей.** Таблица «проверка × прогон × значение × порог ×
  статус» (parquet или ClickHouse) позволяет видеть тренд, а не только последний прогон.
  Отчёт — артефакт прогона в MLflow, статус — результат задачи в Prefect.
- **Пороги задаются в конфиге, не в коде.** Стартовые значения берутся из замеров
  [data.md](data.md).

это известное событие: его размечают, и в следующих прогонах проверка на эту дату
не срабатывает.

## 3. Тесты подготовленных слоёв

| слой | проверка |
|---|---|
| prepared | плотная сетка: каждый день жизненного периода пары есть ровно один раз |
| prepared | суммы сохраняются: продажи в сетке = продажи в сырье по дню × магазину × ветке. Сетка ничего не теряет и не удваивает |
| prepared | у каждой строки есть ветка `кг` / `шт`; ряды без ветки исключены и посчитаны в отчёте |
| prepared | флаг дефицита согласован с остатком; доля дефицитных дней — в коридоре |
| features | **нет утечки будущего**: все исходные даты признака ≤ момента расчёта заказа |
| features | групповые агрегаты посчитаны внутри ветки, `кг` со `шт` не сложены |
| split | train / valid / test не пересекаются по датам и идут по порядку |
| forecast | прогноз неотрицательный, квантили монотонны по `q`, есть все 7 дней горизонта для каждого ряда |

## 4. Тесты кода

`pytest` на маленьких parquet-фикстурах с известным ответом. Например: 3 магазина ×
5 товаров × 14 дней, включая дефицит, отрицательную продажу и товар, выведенный
из матрицы. На них проверяются SQL-шаги, метрики доступности и остатка, разметка
дефицита. Полную выгрузку unit-тесты не читают.

## 5. Мониторинг дрейфа

### Что отслеживаем

**Входные данные:**

- **состав**: число магазинов, товаров и пар в матрице; новые и выведенные позиции;
- **уровень продаж** по ветке, подгруппе и формату магазина — против того же дня
  недели в прошлые недели;
- **распределения**: доля нулевых продаж, доля дней с дефицитом (`StockEndQty = 0`),
  средняя цена `SalesAmount / SalesQty`. Метрики сравнения — PSI или расстояние
  Вассерштейна между последним окном и базой;
- **доля продаж вне матрицы** (`isMatrix = 0`).

**Прогноз и модель:**

- **покрытие квантилей** по сетке `q` — калибровка обычно ломается первой;
- BIAS и WAPE по шагу горизонта;
- **KPI**: доступность (общая и топа) и остаток / списания против целей. Это главный
  сигнал: остальные метрики нужны, чтобы понять причину.

### Правила

- **Всё по веткам `кг` / `шт` раздельно и в разрезах** (формат, подгруппа, топ / хвост).
  Общая цифра прячет дрейф, который сидит в одном сегменте.
- **База сравнения — скользящее окно с учётом дня недели.** Понедельник сравнивается
  с понедельниками, иначе недельный ритм даёт ложные срабатывания.
- **Известные события размечаются**: 2026-05-19, праздники, открытия магазинов.
  Иначе проверка срабатывает на них при каждом прогоне.
- **Срабатывание — это warning в отчёт и уведомление.** Решение принимает человек:
  переобучить, поправить уровень сервиса или разобраться с данными.
- Пороги подбираются по истории проверок. На старте — широкие коридоры, чтобы
  отличить шум от сигнала.

## 6. Инструменты

Основа — собственные SQL-проверки в ClickHouse и тонкий раннер на Python.
Библиотеки — кандидаты, ни одна не выбрана:

- схемы датафреймов в Python — pandera;
- наборы ожиданий с отчётами — Great Expectations;
- отчёты о дрейфе — Evidently.

Решение принимается, когда будут первые SQL-проверки и станет видно, чего не хватает.
